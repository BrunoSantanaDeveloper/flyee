# Apps (modules)

- One directory per app under `modules/<slug>/`, named exactly as `name` in `flyee.module.json`. The reference is `docs/COMO-CRIAR-UM-APP.md`; the procedure is the `app-author` skill; the `apps` skill is the operator's console from the chat. Create a new app with `npm run apps -- new <slug> --type <type> --trail <trail>`, never by hand.
- A new app starts from the catalog (`.claude/rules/catalogo.md`, generated): call existing tool apps through their `references/interface.md`, extend an app that already does part of the job, and propose a separate tool app for a capability several apps would need. Relations are read from what apps ship (`.flyee/modules/<other>/`), never declared twice.
- Apps are used and tried in the workspace, a folder outside this repository (`npm run apps -- link <slug>`; `FLYEE_WORKSPACE` overrides its path). `flyee dev link` refuses to run inside this repository, because it would write the member's harness over the operator's.
- `[PREENCHER]` marks text still to be written (template and `apps bump`); `validate` refuses an app that carries one.
- Required in every app: the manifest, `README.md` (the member's guide and the app page's text), at least one `skills/<name>/SKILL.md` for `skill` and `workflow` types, `tests/eval.json` with at least one case, a `changelog` in the manifest, pt-BR `title` and `summary` (English when the app is published in English), declared `permissions` for everything the app touches, and `external_credentials` for every key the member supplies.
- `files` in the manifest is generated by `npm run pack`; never edit it by hand. `tests/`, `.dev/` and `*.dev.md` never ship.
- A skill's frontmatter follows the Agent Skills standard: `name` equals the directory, lowercase with single hyphens, at most 64 characters; `description` says what it does and when to use it, at most 1024 characters and preferably under 400, because it enters the context of every session. Relative references (`references/`, `scripts/`) resolve from the skill's own directory inside the package, never from the bridge.
- Every app with external credentials has a mode that still delivers something without the key. Every app ships an example prompt in its README ("Peça assim").
- **The member never opens a terminal; the AI does everything.** Apps name the programs they run in `shell` permission scopes, and the CLI installs them (`add`, `update`, `dev link`, `npx flyee need`) through the system's package manager; keys are pasted in a browser page that `npx flyee key set` opens. No shipped text tells the member to install, type or run anything (`validate` refuses install commands and "no seu terminal" in `.md` files). The same holds for the operator: never ask the operator to install a program, run `npm run apps -- link` or the built CLI's `need` instead.
- Keys live outside every project: the AI runs `npx flyee key set <ENV> --json`, which opens a browser page where the member pastes the key (`~/.flyee/keys.json`); an environment variable of the same name wins. Scripts read the variable first (an empty one means no key), then that file; skills never ask for a key in text, never put one in a command and never open the file.
- Versions are immutable: a fix is a new version with a new `changelog`. The first published version is the free one; flagship apps ship 1.0 reduced and 1.1 the same day.
- Automation (`workflow` apps that run on a schedule) has no approval points in the automatic half; decisions belong to the on-demand half. Declare which steps use the member's AI; where there is no reasoning, the step is a script.
- Test an app locally before publishing: `npm run apps -- link <slug>`, then run the skill and the eval cases from the workspace, by hand or with the eval runner when it exists.
