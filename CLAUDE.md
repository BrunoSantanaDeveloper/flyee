# flyee — product monorepo

The PRODUCT of flyee.club: the public npm CLI `flyee` (`npx flyee`), the harness core it installs on the member's machine, and the apps of the catalog. The PLATFORM (accounts, billing, tokens, the package server, the member dashboard and the admin consoles) lives in `C:\AppsProjects\flyee-club` and is never imported here: this repo depends only on its contract (`flyee-club/docs/CLI-CONTRACT.md`) and on the manifest JSON Schema pinned in `schemas/flyee.module.schema.json`. Product decisions are recorded on the platform side, in `flyee-club/docs/PRODUCT.md` ("Decisões tomadas 2026-10-06") and `flyee-club/docs/PLANO-IMPLEMENTACAO.md` (phases 9 and 10); this repo's own plan is `docs/PLANO.md`.

## The boundary: what reaches the member and what never does

Everything the member receives comes through two doors and nothing else:

1. **The npm package `flyee`** (`packages/cli`): the bundled CLI plus `packages/core/assets` copied into `dist/core`. `files` in its `package.json` whitelists `dist`, `README.md` and `LICENSE`; `npm run check:tarball` fails the build if anything else slips in.
2. **An app package** (`dist/modules/<slug>-<version>.zip`): every file under `modules/<slug>/` EXCEPT `tests/`, `.dev/`, `*.dev.md` and tooling leftovers. `npm run pack` computes the manifest's `files` from that rule; a hand-written `files` is a validation error.

Everything else is the operator's material and stays here: `docs/`, `.claude/`, `.codex/`, `AGENTS.md`, `scripts/`, `packages/module-tools`, the evals in `modules/*/tests`, this file. Text under `packages/core/assets` and `modules/*` (outside `tests/`) is read by members and by their AIs: write it for them, in pt-BR with an English version where the manifest asks for it, and never mention internal tooling there.

## Structure

- `packages/cli` — the CLI, TypeScript + ESM, Node 20+, bundled by tsup into one file with zero runtime dependencies (`fflate` is inlined). `src/main.ts` parses arguments and dispatches; `src/commands/*` are the commands; `src/api/*` is the contract client (OAuth, gates, error codes); `src/install/*` downloads, verifies, extracts and writes the adapters; `src/state/*` is `~/.flyee` (device, credentials, app keys, event queue, known projects) and `./.flyee/lock.json` (what is installed in a project). Every command accepts `--json` and `--yes`, because the member's AI often runs the CLI itself. Tests run with `node --test` against `test/fake-platform.ts`, a server that implements the subset of the contract the CLI uses.
- `packages/core` — what the CLI writes into a member's project: `assets/core.json` (the core version), `assets/tools.json` (the declarative registry of AI tools), `assets/agents/*.md` (the managed block of `AGENTS.md`, per language) and `assets/skills/flyee/*` (the `/flyee` menu skill, per language). No code.
- `packages/module-tools` — operator-only tooling, never published: `validate`, `pack` (deterministic ZIP, regenerates `files`), `index`, and the `apps` console (`list`, `new`, `bump`, `link`, `unlink`, `project`, `catalog`, `workspace`). Runs straight from TypeScript with `node --experimental-strip-types`.
- The apps catalog — `.claude/rules/catalogo.md` (always in the AI's context, mirrored into `AGENTS.md`) and `docs/CATALOGO.md` — is generated from `modules/*` by `npm run apps -- catalog` and refreshed by the `catalog-sync` hook after every change under `modules/`; CI fails when it is stale. Who uses whom is read from what apps ship (`.flyee/modules/<other>/`), never declared.
- The workspace — `C:\AppsProjects\flyee-workspace` by default, `FLYEE_WORKSPACE` overrides — is a folder outside this repository where apps are installed as a member would have them (`npm run apps -- link <slug>`), used while other apps are built, and tested. `flyee dev link` refuses to run inside this repository.
- The projects — `C:\AppsProjects\conteudo\<name>` by default, `FLYEE_PROJECTS` overrides the root — are the operator's own brands and clients (MedChina, flyee, Seenaly): one folder each, outside every code repository, where apps are installed the same way (`npm run apps -- project new <name>`, `link <slug> --project <name>`, `project sync`) and real deliveries are produced, so one brand's voice, brand kit and videos never mix with another's. A project is a folder, as in the product: members get the same separation with `npx --yes flyee@latest new <folder>` and `projects`. The workspace stays the test bench.
- `modules/<slug>/` — one directory per app, the unit the platform versions: `flyee.module.json`, `README.md` (the member's guide, also the app page's text), `skills/<name>/SKILL.md`, `scripts/`, `references/`, `guides/<pt-BR|en>/usar.md` and, with depth to show, `abrir-o-capo.md` (the app page in the member area reads only these), and `tests/eval.json` (operator-only). `modules/_template` is the starting point for a new app and is skipped by the tools.
- `recipes/` — named sets of apps with a workflow text, served by the platform API; one JSON per recipe.
- `schemas/` — the manifest JSON Schema as the platform publishes it at `/api/cli/schema/module`; `npm run schema:sync` refreshes it from a running platform and the CI fails on drift.
- `docs/` — `ARQUITETURA.md`, `COMO-CRIAR-UM-APP.md`, `RELEASE.md`, `PLANO.md`.

## Golden rules

- **Contract only.** The CLI calls exactly what `CLI-CONTRACT.md` describes, sends `Authorization: Bearer` and `X-Flyee-Device` on every `/api/cli/*` call, ignores unknown fields, and never builds a platform URL by itself: links come from the server (`action_url`, `links`). Planned fields (contract section 9) are read when present and never required.
- **Verify before extracting.** A package is installed only after its size and SHA-256 match the download response, every entry path is safe (relative, forward slashes, no `.`/`..`, no drive letter) and the archive's file list equals the manifest's `files` in both directions.
- **One copy of an app, bridges everywhere.** The package is extracted once into `.flyee/modules/<slug>/`; every skill gets a bridge `SKILL.md` in `.agents/skills/` and `.claude/skills/` that carries the original frontmatter and points at the canonical file. `AGENTS.md` is canonical, written as a managed block between `<!-- flyee:begin -->` and `<!-- flyee:end -->`; `CLAUDE.md` and `GEMINI.md` get one-line pointers. Always copies, never symlinks (Windows). Never overwrite a file the member wrote: append the managed block or skip and say so.
- **Honest telemetry.** Only the event names and property keys of the contract's allowlist, never content, paths, prompts or project names. Events queue locally and go out in batches of at most 50; the member can read what is queued.
- **Installed apps keep working.** No command ever deletes or disables an app because access ended; only updates stop. A license (contract 9, planned) binds the harness runtime to the machine that downloaded the app; it never expires for use.
- **The member never opens a terminal.** Their AI runs every command: it installs the programs apps use with `npx --yes flyee@latest need` (and `add`, `update` and `dev link` install the ones an app names in its `shell` permissions, through winget, Homebrew or apt, without questions), runs `login` (the member only approves in the browser) and runs `key set`, which opens a one-use page on 127.0.0.1 where the member pastes the key. What only the member can do comes back as `needs_member` with one step (an administrator password, a missing Homebrew). No member-facing text sends anyone to a terminal; `validate` enforces it on apps. The operator is treated the same way: never ask the operator to install something by hand.
- **Keys outside every project.** An app's external key is saved once per machine into `~/.flyee/keys.json` through the browser page of `npx --yes flyee@latest key set <ENV> --browser` (or typed with the echo off when a person runs it in a terminal), never as an argument, or set as an environment variable of the same name, which wins. Apps read the variable, then the file; nothing ever asks for a key in the chat, prints it, puts it in a command or writes it into a project.
- **Apps are products, not personas.** `type` is `skill`, `workflow`, `framework` or `tool`; personas and subagents, when an app needs them, are files inside the app, invisible to the member. The automatic half of a `workflow` has no approval points; decisions belong to the on-demand half.
- **Versions are immutable, the free one is a tag.** A fix is a new version with a `changelog`; the first published version of an app is what the free channel gets (marked in the platform console), so for flagship apps 1.0 ships deliberately reduced and 1.1 the same day. Never maintain a parallel "lite".
- **Windows first.** The operator develops on Windows; every path, spawn and scheduler call must work there, then on macOS and Linux.
- **No `flyee-club` imports, ever.** Shared behavior is re-implemented here against the contract (semver rules, safe paths), with tests.

## Shared Claude/Codex harness

- `CLAUDE.md`, `.claude/rules/*`, `.claude/skills/*` and `.claude/hooks/*` are the canonical sources of this repo's development harness. Codex reads the generated `AGENTS.md` mirror and the generated `.agents/skills/*` bridges; `.codex/config.toml` points its hooks at the same implementations. `PostToolUse` runs `scripts/sync-agent-harness.mjs` after canonical edits; `npm run harness:check` and `npm run harness:test` run in CI. None of this ships to members: the member's `AGENTS.md` and skills are generated by the CLI from `packages/core/assets`, a different thing with a similar shape.
- The `apps` skill is the operator's console from the chat: list, create, change, version, link, use, test and publish apps. `app-author` starts every new app at step 0, the review against the catalog: apps to call at runtime, apps that help build it now, overlaps to extend instead of duplicating, and tool apps worth separating.
- Writing under `modules/` loads the `app-author` skill (hook `.claude/hooks/app-guard.mjs`) and refreshes the catalog (`.claude/hooks/catalog-sync.mjs`); writing under `packages/core/assets` reminds that the text is member-facing; editing the generated catalog is flagged.
- Member-facing text is checked after every write (`.claude/hooks/text-lint.mjs`) and by `validate`, with the same rules (`packages/module-tools/src/text-lint.mjs`): the platform's copy rules block (any dash, exclamation mark, emoji or banned word, in every shipped `.md`, the manifest's texts and the strings scripts print); evaluative AI vocabulary and AI formulas warn, skipping quoted citations. The CLI's own messages are held to the same rules by `packages/cli/test/opening.test.ts`. The `humanizer-pt-br` skill (MIT, from the brunosantanadev repo) rewrites such text; its adapted copy ships to members as the core skill `texto-natural`.
- `.claude/hooks/release-guard.mjs` denies, before they run, the commands that cannot be taken back: `npm publish` and other npm registry changes (the CLI reaches npm only through the release workflow), force push, pushing all tags, deleting remote refs, and `--no-verify`. Quoted text is ignored, so a commit message may mention them.
- Documents that drive work (`docs/PLANO*.md`, audits, evaluations, an app's `.dev/SPEC.md`) follow the `project-doc` skill (from the brunosantanadev repo): state audited with evidence, acceptance someone else can check, declared coverage gaps.

## Commands (root)

- `npm install` — always at the root.
- `npm run validate` / `pack` / `index` — the app tooling over `modules/*` (skips `_template`); `pack` writes `dist/modules/<slug>-<version>.zip` and `.sha256`. A slug after the script name narrows it to one app.
- `npm run apps -- list|new|bump|link|unlink|project|send|catalog|workspace [--json]` — the operator's console (flags go after `--`). `send <slug>` uploads a packed app to the platform as a draft with `FLYEE_SERVICE_TOKEN` (contract section 10), as the "Pack app" workflow does on every app tag. `link` brings the apps an app calls; `--project <name>` targets a brand's project instead of the workspace. `new` scaffolds from the template with `[PREENCHER]` markers that `validate` refuses; `bump` raises the version and blanks the changelog the same way.
- `npm run build` — bundles the CLI and copies the core assets into `packages/cli/dist/core`. `npm run check:tarball` inspects what `npm pack` would publish.
- `npm test` / `npm run typecheck` — every workspace. `npm run ci:verify` — everything CI runs.
- `npm run harness:sync|check|test` — the development harness mirror.
- Try the CLI without publishing: `node packages/cli/dist/flyee.js --help`, or against a local platform with `FLYEE_BASE_URL=http://127.0.0.1:3000`. `flyee dev link ../flyee/modules/<slug>` installs an app from this repo into a scratch project without the platform (`FLYEE_DEV=1`).
